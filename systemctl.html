Ubuntu systemctl

Um serviço é um programa que roda o tempo todo em segundo plano, sem janela: o servidor SSH, o agendador de tarefas, o servidor web. Quem liga, desliga e vigia esses serviços no Ubuntu é o systemd, e você conversa com ele pelo comando systemctl.

Você vai aprender
  • O que são systemd, units e serviços.
  • Ler o systemctl status linha por linha.
  • A diferença entre start (agora) e enable (no próximo boot).
  • Listar serviços rodando e com falha.
  • Usar is-active e os códigos de saída em scripts.
  • Resolver "could not be found", "changed on disk" e serviços que não sobem.

Antes do comando: systemd e units

Quando o computador liga, o kernel inicia um programa: o systemd. Ele é o processo número 1 (PID 1) e é responsável por iniciar todo o resto, na ordem certa: rede, som, login, serviços. Depois, continua vigiando: se um serviço cai, ele pode reiniciá-lo.

Cada coisa que o systemd gerencia é uma unit ("unidade"), descrita num arquivo de texto. O tipo aparece no fim do nome:

TipoO que éExemplo
.serviceUm programa (serviço)ssh.service, cron.service
.timerUm agendamento, como o cronapt-daily.timer
.socketUma porta que liga o serviço quando alguém conectassh.socket
.mountUm disco montadohome.mount
.targetUm grupo de units, como um "estágio" do bootmulti-user.target, graphical.target

Quando você omite o tipo, o systemctl assume .service: systemctl status cron é o mesmo que systemctl status cron.service.

"Daemon"

Programas de serviço são chamados de daemons, e muitos têm nome terminado em d: sshd, systemd, journald. Veja o Glossário.

Ligar, desligar e reiniciar

Estas ações mudam o sistema, então precisam de sudo.

sudo
Como administrador.
systemctl
O programa.
restart
A ação: parar e iniciar de novo.
ssh
O serviço.
$ sudo systemctl restart ssh
[sudo: authenticate] Senha:
$ systemctl is-active ssh
active

Como quase todo comando, o systemctl restart não mostra nada quando dá certo. Por isso conferimos com is-active.

AçãoO que fazQuando usar
startIniciaO serviço está parado
stopParaVocê quer desligar agora
restartPara e iniciaDepois de mudar a configuração
reloadRelê a configuração sem pararServiços que suportam (nginx, ssh); não derruba conexões
reload-or-restartreload se der, senão restartQuando você não sabe se o serviço suporta reload
Esqueceu o sudo?

No desktop, aparece uma janela pedindo a senha (é o polkit, que autoriza ações de administrador). Num terminal por SSH, ele pergunta a senha ali mesmo. Funciona, mas o hábito correto é usar sudo.

Ligar no boot: enable e disable

Esta é a confusão mais comum com o systemd: start liga agora, enable liga nos próximos boots. São coisas independentes.

ComandoAgoraDepois de reiniciar
startRodandoParado (não volta)
enableNão muda nadaLiga sozinho
enable --nowRodandoLiga sozinho
disableNão muda nadaNão liga
disable --nowParaNão liga
sudo systemctl
Como administrador.
enable
Habilita no boot.
--now
E também inicia agora.
nginx
O serviço.
$ sudo systemctl enable --now nginx
Synchronizing state of nginx.service with SysV service script with /usr/lib/systemd/systemd-sysv-install.
Executing: /usr/lib/systemd/systemd-sysv-install enable nginx
Created symlink '/etc/systemd/system/multi-user.target.wants/nginx.service' → '/usr/lib/systemd/system/nginx.service'.
$ systemctl is-enabled nginx
enabled

O enable cria um link dentro de multi-user.target.wants. É assim que o systemd sabe o que ligar no boot: tudo que o estágio multi-user.target "quer" (wants). As linhas "SysV" aparecem em serviços que também têm um script antigo de inicialização; podem ser ignoradas.

Proibir de vez: mask

disable só tira do boot: outro programa ainda pode ligar o serviço. mask impede que ele seja ligado de qualquer forma, até você rodar unmask:

$ sudo systemctl mask cups
Created symlink '/etc/systemd/system/cups.service' → '/dev/null'.
$ sudo systemctl start cups
Failed to start cups.service: Unit cups.service is masked.
$ sudo systemctl unmask cups

O que o comando devolve: perguntas para scripts

Três ações respondem com uma palavra e um código de saída, perfeitas para scripts:

$ systemctl is-active cron
active
$ echo $?
0                                   « 0 = sim, está ativo
$ systemctl is-active cups
inactive
$ echo $?
3                                   « diferente de 0 = não
$ systemctl is-enabled cron
enabled
$ systemctl is-failed meuapp
failed

Num script, use direto no if, sem imprimir nada (--quiet):

#!/usr/bin/env bash
if ! systemctl is-active --quiet nginx; then
    echo "nginx caiu! Reiniciando..."
    sudo systemctl restart nginx
fi
Código de systemctl statusSignificado
0Ativo
3Parado ou com falha
4A unit não existe

Ver e ajustar o arquivo de um serviço

Ler: cat

$ systemctl cat cron
# /usr/lib/systemd/system/cron.service
[Unit]
Description=Regular background program processing daemon
Documentation=man:cron(8)
After=remote-fs.target nss-user-lookup.target

[Service]
EnvironmentFile=-/etc/default/cron
ExecStart=/usr/sbin/cron -f -P $EXTRA_OPTS
IgnoreSIGPIPE=false
KillMode=process
Restart=on-failure
SyslogFacility=cron

[Install]
WantedBy=multi-user.target

A página Criar um Serviço explica cada linha.

Ajustar sem mexer no original: edit

Nunca edite os arquivos em /usr/lib/systemd/system/: uma atualização do pacote apaga sua mudança. O systemctl edit cria um arquivo de "ajuste" (override) separado, em /etc/systemd/system/cron.service.d/override.conf:

$ sudo systemctl edit cron

Abre um editor; escreva só o que quer mudar, entre as linhas de comentário indicadas, por exemplo:

[Service]
Restart=always
RestartSec=5

Ao salvar, o systemd recarrega a configuração sozinho. Depois, reinicie o serviço.

Mudou um arquivo à mão? daemon-reload

Se você editou ou criou um arquivo .service diretamente, avise o systemd:

$ sudo systemctl daemon-reload

Formas diferentes de fazer

FormaExemploObservação
systemctlsudo systemctl restart sshA forma atual e completa
servicesudo service ssh restartComando antigo, ainda funciona; repare na ordem invertida
Interface gráfica—O Ubuntu não traz uma tela de serviços; o terminal é o caminho
Serviços do usuáriosystemctl --user statusServiços que rodam como você, sem sudo (ex.: o som, pipewire)

Desligar e reiniciar a máquina

$ systemctl reboot        # reiniciar
$ systemctl poweroff      # desligar
$ systemctl suspend       # suspender

No desktop, com você logado, não pedem senha. Num servidor por SSH, use sudo.

Quando não funciona

"could not be found" 
$ systemctl status apache
Unit apache.service could not be found.
$ echo $?
4

O que aconteceu: não existe serviço com esse nome. O nome pode ser diferente do programa: no Ubuntu, o Apache é apache2 e o SSH é ssh (não sshd).

Como resolver: procure o nome certo:

$ systemctl list-unit-files | grep -i apache
apache2.service                              enabled         enabled
"changed on disk" 
$ sudo systemctl restart meuapp
Warning: The unit file, source configuration file or drop-ins of meuapp.service changed on disk. Run 'systemctl daemon-reload' to reload units.

O que aconteceu: você editou o arquivo do serviço, mas o systemd ainda está usando a versão antiga.

Como resolver: sudo systemctl daemon-reload e depois sudo systemctl restart meuapp.

O serviço não sobe (failed) 
$ sudo systemctl start meuapp
Job for meuapp.service failed because the control process exited with error code.
See "systemctl status meuapp.service" and "journalctl -xeu meuapp.service" for details.

O que aconteceu: o programa iniciou e saiu com erro. A causa está no log.

Como resolver: faça o que a própria mensagem sugere: journalctl -xeu meuapp. As causas mais comuns são erro no arquivo de configuração, porta já em uso e caminho errado no ExecStart. Siga o roteiro completo em Logs (journalctl).

Liguei o serviço, reiniciei e ele não voltou

O que aconteceu: você usou start, mas não enable.

Como resolver: sudo systemctl enable nome. Confira com systemctl is-enabled nome.

Exercícios

1. Ligar agora e no boot

Complete para iniciar o ssh agora e fazê-lo ligar em todo boot, num comando só:

sudo systemctl enable ssh

2. Algo falhou?

Complete para listar todas as units com falha:

systemctl

3. Editei o arquivo do serviço

Você mudou /etc/systemd/system/meuapp.service à mão. Complete o comando que faz o systemd reler os arquivos:

sudo systemctl

4. Você rodou sudo systemctl start nginx e reiniciou o servidor. O nginx está rodando?

5. No systemctl status, o que significa Active: failed (Result: exit-code)?

Resumo

  • systemd é o PID 1: inicia e vigia os serviços. Você fala com ele pelo systemctl.
  • status mostra tudo: se liga no boot (Loaded), se está rodando (Active), o PID e o log recente.
  • start/stop/restart valem agora; enable/disable valem para o boot; --now faz os dois.
  • is-active, is-enabled e is-failed devolvem códigos para scripts.
  • Falhou? systemctl --failed e journalctl -xeu nome. Editou o arquivo? daemon-reload.
